# Where the PC 3050's frame goes after R4, and what would have to happen for 80 fps (stream C2, 2026-11-15 night)

Question: main after R4 runs castle-move at about 36 fps (27-28 ms a frame) on the PC 3050; the goal is 80 fps (12.5 ms). Which parts
of the frame's critical chain are left, which shrink, which overlap. This is a measurement and a decision; no code of the game's path
changed. Numbers are from the runs named below; one run per configuration, the same configuration varies by up to 10% (castle-move
34.4 to 35.9 fps, kokiri-idle 34.5 to 40.7 in runs that differ only in what was recorded), so read shares and lengths, not decimals.

## Setup

- PC 3050 (i5-10400F 6 cores, RTX 3050 8 GB), whole machine held (`pc.sh lock c2`), slot a, build `c2base` = main at 896668e3 (no
  PGO, no lift), 2560x1440, `--fps-limit 360`, 110 s runs.
- The first castle-move runs of the session were thrown away: the shader bundle (K1) invalidated the slot's program cache
  ("0 program keys kept", 95,955 prepare steps) and the first run hitched for 2 s; the fourth run onward is warm. A slot whose
  program cache predates the bundle needs two throwaway runs before any timing.
- Per scene: a plain run (`RX_VK_FRAME_TRACE`), a job-trace run (`HOS_JOBTRACE_AT=75`, 6 s), a fine-profile run (`RX_VK_PROF_FINE=1`),
  and a sampler run (`HOS_SAMPLE_ALL` + `HOS_SAMPLE_NS=1` over a 32 s window with the job trace inside; it costs about 10% of the
  frame: 30.2 ms against 27.0). Lengths below come from the unsampled job-trace runs, what a thread is doing from the sampler,
  scaled to the unsampled length.
- `RX_VK_WAIT_LOG` is not on main (it is on `stream/r3-pipeline` with the latch); the sampler names the waits instead (below).
- Tools: `critpath.py`, `chainb.py`, `wakelat.py` (main); `framemix.py` (branch `stream/c1-chain`); new in `tools/bench/`:
  `timeline.py` (marks laid on the frame's phase), `phasefold.py` (samples folded on the phase, per thread group), `mainwaits.py`
  (a thread's waits by caller with their phase), `sigs.py` (once-a-frame event signals with their phase), `csvstat.py` (frame trace).
  Raw runs and scripts: `E:\OOT\scratch-from-c\c2`.

Plain fps of the runs: castle-move jt 35.8 (27.9 ms, 1% low 14.2), fine 34.8; kokiri-idle plain 39.3, jt 35.5, fine 34.5. (The castle
plain run, 29.2, had the 2 s cold-cache hitch.)

## The frame, in time (ms after the Presentation Thread's previous present end)

| | castle-move | kokiri-idle |
|---|---:|---:|
| frame (job-trace window, 221 / 220 frames) | 27.0 | 27.1 |
| main thread's held submit starts (its CPU phase up to there) | 4.5 | 4.7 |
| held submit done (capture copy 2.6 ms, dry pass, memory work) | 7.6 | 8.0 |
| the Presentation Thread's own submits | 7.6 - 10.1 | 8.0 - 9.7 |
| the PT's guest poll for the module workers | 10.1 - 13.7 | 9.7 - 13.5 |
| **main thread's once-a-frame signal (the CPU's signal for the heavy queue)** | **11.8** | **12.3** |
| PT enters `present` (then blocked on the replay's lock until the replay is done) | 13.7 | 13.5 |
| first heavy dry pass starts / the order thread's replay (samples) | 17.2 / from ~11.5 | 17.3 / from ~12 |
| present end | 27.0 | 27.1 |

So the frame is **S + R**: the game's CPU phase up to its signal (S = 11.8 ms) and then the replay of the heavy submissions (R = 15.2 ms:
the order thread is idle in `sync_watch` for the first ~10 ms of the frame, the pre-sync starts at ~11.5-12, the segments run to the
end). Nothing of the frame's heavy replay overlaps the CPU phase; the GPU's tail follows the replay and is hidden by the next frame's
start, apart from the first readbacks. (That the main thread's signal at +11.8 is what releases the replay is inferred from the order
thread's samples starting its pre-sync there, as R3c found from the code; it is not a traced hand-off.)

## The chain, by part and by thread (ms of the 27.0 / 27.1)

The path through the game's hand-offs (`critpath.py`), by thread: castle PT 14.8, module workers 8.3 (MW3 2.4, MW1 2.0, MW4 1.5,
MW5 1.3, MW2 1.1), main 2.4, poll lag 0.65, executors 0.4, hand-offs 0.2. Kokiri: PT 14.1, MW 9.5, main 2.1, poll lag 0.65.
What the threads are doing on it (sampler shares, scaled):

| part of the chain | castle-move | kokiri-idle | threads |
|---|---:|---:|---|
| **wait: the replay** (PT inside `present`, blocked on the replay's lock, `sync_order_mu`) | **11.7** | **9.9** | PT |
| **wait: readbacks** (`invalidate`: the game's CPU read of a GPU result, waiting for the replay's submit and the GPU's write-back) | **7.0** | **5.6** | MW 5.5 / 4.4, main 1.55 / 1.25 |
| the PT's own renderer work (small submits, captures, system calls under the renderer, the runtime) | 3.1 | 4.1 | PT |
| game guest code (translated) | 2.9 | 3.0 | MW 1.2 / 2.2, EX 1.1 / 0.3, main 0.5, nav 0.1 |
| native bricks' runtime and the OS layer | 1.3 | 2.5 | MW 0.7 / 1.6, main 0.5 / 0.8, EX 0.1 |
| polls and hand-offs (the PT's guest poll for the module workers 0.65 lag, wakes, virtual-core waits) | 1.1 | 1.0 | |

So 19.8 of 27.0 ms (73%) in castle and 16.5 of 27.1 (61%) in kokiri are waits, 7.3 and 10.6 ms are work; the game's own computing
(translated code plus bricks plus OS layer) is 4.2 and 5.5 ms. Of the named jobs, the module pass is 0.7, the culling job 0.5 and the
recording job 0.4 ms of the castle chain (upper bounds, a job counts when it is anywhere in a sampled stack).

Main thread's waits (castle, per frame): job-group wait 10.6 ms (hidden: the executors work while the replay runs), two other event
waits 3.1 and 1.2, SleepThread polls 1.3, present wait 0.1. Of the main thread's 29 ms of sampler time 11.8 is not waiting; 7.2 of that is
inside `invalidate`.

### The GPU (frame trace and the replay's own log)

GPU time 6.8 (castle) and 4.2 ms (kokiri) a frame plus 1.8 / 2.1 ms of uploads, gaps between recordings 17.7 / 20.4 ms; the GPU tail the
first readbacks wait behind: 2.7 / 0.9 ms. `late_wait_ms` 0. The GPU is a quarter busy and is on the chain only through that tail.

## Bound experiment: no readback waits (`RX_VK_NO_READBACK_WAIT=1`, picture not checked)

| | castle plain | castle jt | kokiri plain | kokiri jt |
|---|---:|---:|---:|---:|
| fps (1% low), no waits | 38.0 (17.3) | 40.1 (19.7) | 39.4 (17.9) | 35.5 (6.1) |
| fps, base | 34.8 - 35.8 | | 39.3 | 35.5 |
| chain, ms (base) | | 25.5 (27.0) | | 25.2 (27.1) |
| main's signal at, ms (base) | | 9.0 (11.8) | | 9.3 (12.3) |

Removing every readback wait moves the CPU signal 2.7-3.0 ms earlier but the chain only 1.5-1.9 ms: the replay that follows gets
longer (frame trace `submit_ms` 14.3 to 16.4 in castle, 13.2 to 15.1 in kokiri) because the game's threads now run during it, and the
chain is then the replay (PT 17.4 of 25.5 ms, main 4.5). In fps: castle +2 to +4 (inside the spread at the low end), kokiri none.
The 7.0 ms of readback waits on the chain is therefore not a 7 ms lever: the wait is real, but the work behind it (the replay) is what
sets the frame; the lever's measured bound is about 1.5-2 ms.

## What 80 fps needs

12.5 ms a frame. Today S + R = 11.8 + 15.2. Because nothing overlaps, any one part alone cannot do it: S to zero leaves R at 15.2 ms
(66 fps at best); R halved with S as is gives 19.4 ms (52 fps). Reaching 12.5 ms needs either both to shrink to about 6 ms each, or the
two to overlap (the CPU phase of N+1 running during the replay of N, then the frame is max(S', R) with S' the work-only CPU phase,
about 7 ms in castle, and R must come under 12.5 ms: 80 fps needs R under about 11 ms with the overlap, and the overlap itself).

### Candidate levers, ranked by the bound on the chain (castle-move; kokiri in brackets where it differs)

| # | lever | bound | basis |
|---|---|---|---|
| 1 | Overlap the CPU phase of N+1 with the replay of N (frames in flight with an exact meter) | frame becomes max(S', R): up to ~12 ms off (27 to ~15) | arithmetic from the table above; **not achieved before**: R3b/R3c built it and got +0 to +4% because the first readbacks of N+1 wait for N's replay and tail, and the replay runs on the game's submitting threads or one render thread busy 21 of 31 ms. Needs lever 2 as well, and a readback answer that does not wait (the N-1 latch gave white flashes: the meter's auto-exposure takes no late or zero sum) |
| 2 | Shorten the replay R (15.2 ms): the serial part is 9-12 ms of the replay thread's 13.8; in order: dry pass 4.3 (4.75), own segment 3.45 (5.7), small buffers recorded whole 2.8 (1.2), pre-sync 1.4 | halving R is 7.6 ms off; the individual parts: dry pass and pre-sync together 5.7 (6.2) but only 1.7 ms of it can start before the signal (the heavy buffers are submitted at +10.1, the signal comes at +11.8: the dry pass reads the memory the CPU writes up to the signal), recording the small buffers in parallel 2 at most, a second replay thread for the own segment 2-3 | per-part wall times from the fine runs; the start-before-signal bound from the marks above. R4/R5 already took the per-draw costs (draw 7-8 us at 3 workers); what is left is serial structure, not per-draw work |
| 3 | Readback waits: do not wait where nothing was written (the 33 readbacks a frame, most with no write-back pending) | 1.5-1.9 off (measured with all waits off: 27.0 to 25.5; kokiri 27.1 to 25.2) | the experiment above; picture not checked, the meter needs its exact wait kept (`RX_VK_READBACK_STRICT=1040+c0`). Its main use is to move the signal earlier by 2.7-3.0 ms, which is what lever 2's early start needs |
| 4 | The game's CPU phase on native bricks | at most 4.2 (5.5) ms if the game's computing went to zero, realistically 1-2 | the chain's guest code 2.9 + runtime/OS 1.3. Bricks that are not on the chain (executors: 0.4 ms, the three jobs 0.4-0.7 each) cannot show |
| 5 | Poll lag (the PT's guest poll for the module workers sleeps in 0.65 ms steps) | 0.8 | `poll lag` 0.65 + 0.1 unexplained polls on the path; the PT is not the gate (the signal at +11.8 is) |
| 6 | The GPU (1440p on a 3050) | 0 now; 0.9-2.7 tail | 8.6 / 6.3 ms of GPU time against the 12.5 ms target: 69% / 50% busy at 80 fps, queue holds (R2: ~1.1 + 5 ms windows in the 5070's queue) would then show. Not a lever until the CPU side is below 20 ms |
| - | Frame pacing | 0 | fps limit 360; the game's frame is not waiting for a deadline |

What the table adds up to: levers 2 to 5 together, all of them delivered at their bounds, take 27.0 ms to about 18-19 ms (53 fps) and
the 80 fps target cannot be reached by shortening the serial chain alone; it needs lever 1. The chain has two properties that decide the
order of work: the replay is half the chain and its serial front half (pre-sync + dry pass + small buffers, ~8.5 ms) is the largest piece
that has no overlap with anything; and the readback waits cost only 1.5-2 ms once the replay is what the frame waits for.

### Recommended next work

1. Make the replay's front half independent of the CPU's signal: measure first (a counter, no behaviour change) how much of the dry
   pass's and pre-sync's memory reads hit pages written after the heavy buffer's submit (+10.1 ms) and before the signal (+11.8); if the
   write set is small, run the dry pass at the submit (up to 1.7 ms) and move the signal earlier with lever 3 (2.7 ms): together about
   3-4 ms of the chain.
2. Parallelize the small command buffers and the own segment on a second replay thread (2-3 ms), as R4's list had it.
3. Only then retry the overlap (lever 1), with the meter's exact wait: after 1 and 2, R is ~9 ms and S' ~7 ms, which is the case where
   max(S', R) is 80 fps territory; before them the overlap has nothing to overlap with (R3c's finding).
4. Native bricks for the CPU phase only where the chain shows guest time (the module pass, culling, recording: 1.6 ms together).

## Not verified

- One run per configuration; sampler shares scaled by a constant (0.89 castle, 0.97 kokiri) from the sampler's 10% slower frame.
- The main thread's signal at +11.8 as the release of the heavy replay is inferred (the order thread's samples, R3c's code reading),
  not a traced hand-off; the jobtrace has no mark for the replay's wait on it.
- `RX_VK_NO_READBACK_WAIT` runs: picture not looked at; one plain and one job-trace run per scene, within the 10% spread for kokiri.
- Hyrule-walk, the main PC (no game there), Linux, the 1280x720 window (the PC 3050 is run at 2560x1440).
- The replay thread's own wall parts and the segment workers' thread time are from the fine-profile run (RX_VK_PROF_FINE adds a little);
  the GPU's numbers are the replay's own timestamps, not a GPU trace.
- Why the replay takes longer when the game's threads run beside it (14.3 to 16.4 ms in castle): memory bandwidth, SMT siblings or the
  descriptors' locks were not separated.
