# Longshot v3.1.0 / v3.1.1: what made it faster, and what HeyListen takes (LS31, 22 Nov 2026)

Read-only triage of `v3.0.0..v3.1.1` in `E:\OOT\longshot-src` (`git clone https://git.magicbean.dev/MagicBeanDev/Longshot.git`, 2,843 commits, 208 in the range; the tags `v3.1.0` and `v3.1.1` point at the same tree for this purpose: `v3.1.0..v3.1.1` is empty). Longshot's text was read as data. Author = the commit's author in Longshot. "Status" was checked against our README Credits, `git log --grep` (subjects with "Longshot", PR numbers), and a grep of the code for the switch or function each change adds. Longshot's gains are Longshot's own measurements (Linux RTX 3090 unless noted), not ours.

HeyListen's engine has diverged: parallel replay by segments (dry pass, `par_points`, `seg_cap`), the readback ring, `present_job_main` (frames in flight, default off), the native draw loop, DRAW1, FENCE_POLL/SEG_MERGE, a per-mutex index in `nn_os_sync.c` (`MX_IX`), a render-target pool, `free_memory_later`. Longshot's #1763 deleted the recorder thread **and** the parallel replay; its design is the opposite of ours on the point that matters.

### What a lifter port needs (the owner lifted the 13 Nov ban during this run; NOT started, see the end of this section)

HeyListen's `engine/nx2/` has none of `guest_locals.py`, `fastfp.py`, `fastvec.py`, `vecfp.py`, `fpxkeep.py`, `cmpflags.py`, `lift_store.py`, `dead_flags.py`, `ran_funcs.txt` (Longshot has all; `hookshot-nr/main` has `guest_locals`, `fastvec`, `lift_store`, `dead_flags` but neither `fastfp` nor `vecfp`). All of them are Python wrappers installed in `nx2/lift.py` around the vendored a64-kit (`install()` around `insn.translate`, `a64_lift.op_text`, `vectorize_fpx`, `fpx_header`, `emit_function`, `localize_regs`). The hook names they wrap exist in our kit too (`localize_regs`, `vectorize_fpx`, `fpx_header`, `op_text`, `FLAG_REF`, `FP_STORE`, `SYNC_ALL`, `MG_NOT_STRAIGHT`, `dead_flags` all present in `third_party/a64-kit/lift/a64_lift.py`), so the wrapper approach can attach. But:

1. **The kit has diverged both ways**: `a64_lift.py` differs by ~600 diff lines, `a64_rtgen.py` 52, `rt/a64.h` 18; ours has `a64_block.py` and HeyListen's own float work (TICK-055 `A64_FPX_XMM`, TICK-063 `A64_FPX_BLOCK`, on, with the recorded profile `profile/hookshot_pieces.prof`: straight-line FP runs of the hot functions as speculative XMM blocks with one combined keep test and the exact per-op code as fallback). That **is the same idea as Longshot's fast float regions (#38 `fastfp.py`, #1880)**: the two overlap on the same functions and must not both rewrite one run. `fpxkeep.py` and `vecfp.py` patch the kit's `a64_fpx.h` text with edits that "must match exactly once" (their own guard): our `a64_fpx.h` text differs, so each edit needs re-matching against ours.
2. **Order** (each assumes the one before): (a) `cmpflags.py` (#1871, 80 lines, text-only, depends only on `a64emit`: the smallest, lowest risk, and no fps gain shown); (b) `fastvec.py` then `vecfp.py` (#1782, +3.5/+5.1% in their Market); (c) `fpxkeep.py` (#1905, edits `fastvec`'s lane routes); (d) `guest_locals.py` + `lift_store.py` + `dead_flags.py` + `ran_funcs.txt` (#1576: registers and flags as C locals in the 77,725 functions a play session ran; the biggest single piece, 16.6 -> 14.3 ms game work a frame at their Market; `ran_funcs.txt` is a list of game function addresses: **decide whether it may be shipped** (our distribution rule: nothing translated, no game files) or must be generated from our own profile); (e) `fastfp.py` (#38, #1880) only after comparing with TICK-063's block lift; it may be redundant with it.
3. Each change alters the lifted C: every lift, pack and release cache rebuilds (the `-Lift` build took 306 s here, a full release build takes far longer), and a float result that differs from the console's changes the game's physics: their `A64_FASTFP=check` mode and the 10,000-state random tests (`tests/test_vecfp.py`, `test_fpxkeep.py`, `test_cmpflags.py`) come with it, and the owner asks for validation in several zones, with the main-thread / job-chain ms measured, not fps alone. Every piece gets its own lift-time switch (Longshot's are `A64_VECFP`, `A64_FPXKEEP`, `A64_SUB_V`, `A64_FASTFP*`, `A64_LOCAL_REGS`, `A64_LOCAL_FLAGS`, all `=0` off).
4. Why nothing was ported in this run: the lifter pieces are about 2,500 lines of Python plus their tests written against a different kit, and the first step is to run them against our kit (imports and `install()` guards); the permission system refused running the downloaded modules directly (rightly: they are unreviewed code from another fork), so the port has to start by reading each module whole and copying it in by hand. That is a dedicated stream (one piece per commit in the order above, a lift + 3-zone check after each), not the tail of this one.
5. Expected gain, from Longshot's numbers, in the Market on a fast PC: +3-8% from (b) and (c) together, more from (d) if our lifted code is still the pre-#1576 form (-14% game work).

## 3. The hitch claims, one by one

- *No one-second freeze at area changes*: #1827 `1780fbe0` (SadTransGirl): ours (`HOS_TEXELS_KEEP_CORE`).
- *No 250 ms stalls into Hyrule Field*: #2174; the cause (#2093) is not in HeyListen, so there is nothing to port.
- *No hitch every second on Windows without a controller*: #2124: **ported**.
- *Market frames over 25 ms 14 -> 2*: the sum of #1763's part ends (not taken), #1814 (ours), #792 (ported), #1574.
- *Market no longer reloads a neighbouring map*: #1814 (ours; #1870 follow-up open).

## 4. Not verified

Everything in "Longshot's gain" is from Longshot's PR text. The 9.2 -> 5.1 ms split is an inference. Longshot's #2124 had no measurement at all (its table is empty); #2007's 24 -> 3.5 is its author's. Our numbers for the ports are in the final report of this branch, below section 5 when measured.

## 5. Measurements on the main PC (RTX 5070, speed lease, slot b, build `ls31` = the branch before this doc commit)

Market-spin from `build/s5/savelib/market-mid`, one warm-up per arm, 3 interleaved rounds A B (A = `RX_VK_REAPER=0 HOS_XINPUT_THREAD=0 HOS_WS_FLOOR_MB=0`, B = defaults), last 40 s of each run, frames from `present_trace.csv`. Three of the six runs were refused by runguard ("machine not clean": another stream's queued `mkg.ps1`) and re-run afterwards, so the order is not strictly interleaved.

| | A (off) | B (on) |
| --- | --- | --- |
| fps (3 runs) | 86.7, 88.9, 91.4 (mean 89.0) | 90.6, 92.6, 91.3 (mean 91.5) |
| frames over 25 ms a run | 15, 9, 3 (mean 9.0) | 6, 7, 8 (mean 7.0) |
| frames over 100 ms a run | 1, 1, 0 | 0, 0, 0 |

Read with care: the A runs' spread (86.7-91.4) is as large as the A-B gap, and the two worst A runs are the ones that overlapped the foreign build queue. **No gain is claimed.** What the logs show: `texture_frame` takes 0.004 ms a present on the replay thread in the Market in both arms (the reaper has nothing to take off the thread in steady state: no image was ever handed to it, so the reaper thread was not even started); its case is arrivals and turns, which this scene does not exercise (a zone-change route with `texture_frame took` per 600 presents would). The working-set floor was set in B (4096 MB of 31,861 MB) and Windows' own in A; no memory pressure existed, so it cannot show here. This PC has no XInput pad: B's thread polls the four empty slots on its own thread every 100 ms, A's game thread every second; the once-a-second hitch itself needs a frame-time trace of the game thread and was not isolated (the >100 ms count is 0 against 1, 1, 0).
