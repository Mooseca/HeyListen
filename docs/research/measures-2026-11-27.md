## Do not redo (what is already settled)

- The cost of the order thread's clean arms on the 3050 (section 1, list r4): join 3 is slower than the order thread off
  in the Market. Do not re-run it as a default candidate.
- The steady-play lows at the 60 limit on the 3050 are the replay's CPU path, not the GPU and not hitches (section 2).
  The first fix tried for the upload hitches (upload conversion outside the replay lock) gives no gain.
- The levers `RX_VK_PARALLEL_IDEAL` and `RX_VK_MID_SEG` on the 3050 (section 3): nothing large. The first became a
  default by a rule; it is equal on the laptop and was A/B-tested on the main PC only as a gate (4 noisy runs).
- The order thread's flash: the cause is the meter's companion block being overwritten with a stale copy (section 4).
  The "lost update", the "overtaken zero", "pacing, not data" and "staleness of the sums" readings are all refuted or
  superseded (section 7).
- The laptop's amdvlk64 crash is a driver abort when GPU-reachable memory is full (section 6).
- The detector's own frame dumps make flashes with the order thread on: measure with `RX_VK_FLASH_DUMPS=0`.

### The rule it became (main 485cb4386, then 7fd6151b7)

`gpu/vk/par_ideal_rule.h`, `tests/test_par_ideal_rule.py`. Fast cores only (EfficiencyClass), without the first core (the
game's main thread) and without the host's reserved core (the replay thread's). By default the hint is given only where
every worker gets a core of its own: 6c/12t with 4 workers: 2 4 6 8 (the placing r5 measured); 8c/16t with 5 workers: 2 4 6
8 10. 4c/8t and 6P+4E hybrid with 5 workers: no hint by default, not measured there. `RX_VK_PARALLEL_IDEAL=0` off, `=1`
shares the cores in turn. The old code would have sent every worker to one core on a 2-core CPU and used a hybrid CPU's
small cores. Known flaw: `docs/SWITCHES.md` prints "Default: unset" for it.

CI on 485cb4386 was red: the Linux build (AppImage) did not compile `vk_replay.cpp` (the Windows layer has the older
`GetLogicalProcessorInformation` only); the Windows and WSL suites do not compile the renderer for Linux. Fix 7fd6151b7
(extended call under `_WIN32`); the Linux syntax check (clang++ `-fsyntax-only` with the builder's Linux flags) gives 13
errors on 485cb4386 and 0 on the fix. CI green on 7fd6151b7 (run 45971312653). The check found the same break in
`vk_trace.cpp` (`CreateFileMappingA` unguarded), fixed in f1faf0a84. Gate chain18: Windows suite 584 passed / the 3 known
failures, WSL 598 / the 4 known; chain19: Linux syntax 0 errors.

### 4.2 FLICK1: the first mechanism and the pacing fix (main PC, build flick1k, RTX 5070)

The "lost update" hypothesis (a late write-back rolling back a CPU write) is refuted: with `HL_WB_CLOBBER` +
`HL_WB_SHADOW_ALL` no CPU store is overwritten by a write-back in any range. A rare other rollback exists (a capture taken
at hand-over can predate write-backs not yet recorded); a GPU merge `RX_VK_SYNC_KEEP_GPU` was built for it, changes no
flash count and ships off.

Mechanism, proven by causing it on demand: the game's module job reads the exposure meter (three 0x1040 blocks) once a
frame; with the order thread the present is not held by the replay; if that job runs late, the present is handed over
while it is still reading and the next frame's whole 3D scene is brighter (about +5 of 255, HUD unchanged). Forced delay
of 12 ms every 60th frame (Kakariko standing, 60 limit): order thread on 131 delays, 132 strict flashes, each one present
after a delay; order thread off 122 delays, 0 flashes. Unforced: every strict flash is a frame whose last meter read came
after its present's hand-over (3 of 3; about 94 times above chance in another run).

Pacing fix (`rbring_meter_pace`, `vk_rbring.cpp`, order thread only, `RX_VK_ORDER_METER_PACE_MS` 20, 0 = off,
`tests/test_meter_pace.py`): the hand-over waits, 20 ms at most, for as many meter reads as the last 16 frames had made. Strict
flashes with forced delay: pacing off 132 and 73; pacing on 1 and 1 (the first delay, before the rule had learned);
order thread off 0. With a forced replay hitch: off 14, 2, 5, 2, 3, 3; on 0, 1, 0, 0; join 3: 2. Cost: 0-5 waits per 3600
presents of 1-2.7 ms, never the 20 ms bound. Five starts fine. The detector's own dumps stall the replay about 5 s each
and with the order thread that makes a flash, which dumps again: still-scene counts of MAP1 and Mooseca were partly this;
a clean 600 s still run with `RX_VK_FLASH_DUMPS=0` gives 0.

Clean branch `fix/order-meter-pace` 50792c7cb (build flick1m), forced delay 12 ms every 60th frame, Kakariko standing, 60
limit, order thread on, `RX_VK_FLASH_DUMPS=0`, 180 s: pacing on 116 delays, 0 strict flashes; pacing off 121 delays, 124
flashes. Three starts fine. Gate chain17 for int1127b: passed; merge put on hold (see 4.3).

### 4.5 The cause and the no-wait fix (build flick1v3, branch `fix/order-meter-pace` tip b7df227f9 on 485cb4386; bundle `flick1-v2.bundle`)

Cause, found by a diff of captured pages around forced late jobs: not the sums, not the scene block's exposure words. It is
the meter's 0xc0 companion block (page 0x11371e7000, words +0xf30..+0xf54), which the game's job invalidates and then
fills whole for the GPU and never reads. The read-back ring answered the invalidate by writing its staged GPU copy (3
frames old) into guest memory; the job's fill overwrote it; with the job late past the hand-over the next capture took
the page between the two writes, and the GPU read its own old floats as the game's parameters for one frame.

Fix: `rb_c0_keep` in `vk_rbring.cpp`: a 0xc0 read writes nothing and returns before any wait; switch `RX_VK_RB_C0_KEEP` (1;
0 = before); the pacing stays as a fallback, off by default. Rebased on main f1faf0a84 as tip 1fed11044 (switch lists
regenerated; Linux syntax ok; its two tests run), pushed as `wip/order-meter-nowait`.

## 5. The exposure formula, renderer side (main PC, MAP3's reading, 10:02)

What is measured: the meter never reads the picture. Before the frame's first draw two compute programs place 16x16
points on the screen, read the previous frame's depth and rebuild world positions. One gives the fraction of points in the
sun's shadow (cascades plus mask); the other gives the mean luminance of the baked light probes there (already scaled by
the current exposure). Output: a 16-byte header of sums plus a 256-entry table (4 + 1024 = 1028 words: not a histogram). A
third block (inner mask) never ran.

The CPU side, once a game frame, 2-3 frames after the GPU measurement, in plain arithmetic. With SA, SB, SC the three sums
and k, lo, hi per-environment data:
- vA = 1 - k * (1 - SA/256)
- vB = 1 - clamp01((SB/256 - lo) / (hi - lo))
- vC = SC/256
- each goes through a 15-sample moving average (ring of 30): avgA, avgB, avgC
- EV = base + a * avgA + b * avgB (base, a, b, lo, hi per environment)

Kakariko worked example: base 14, a = b = -1, lo 0.08, hi 0.2; avgA 0.5498, avgB 0.0665 give EV 13.384; the object holds
13.38. 150 watched averages replayed, mean error 0.003.

Way back to the picture: EV, 2^-EV and 2^(EV-14) are written in the per-frame scene constants block (+0x380..+0x38c, two
buffers by frame parity) and a 0x200 block; the lit passes multiply light by 2^-EV (35 fragment programs, inferred per
program); no final tone pass; the HUD is untouched.

Timing: depth of frame N-1, read 2-3 frames later, 15-frame ramp: a step settles in 18-20 frames; full shadow = up to 1
stop. Saturated averages (0 / 1) are normal output (day Field: every sample sunlit). A reset flag in the exposure module
clears the windows and freezes A and B for two frames; who sets it is not mapped.

Flash size check: a set one frame old moves EV by under 0.03 (under 1/255), so staleness alone cannot be the +3 to +16 of
255. (The wrong-sample inference of 1/15 of an average = 0.067 EV = up to 12 of 255 was sent to FLICK1 as untested; the
cause found afterwards is a different one, section 4.5.) Redesign facts: everything after the sums is small and exact and
could run on the GPU right after the measurement and write the exposure words itself; the CPU still reads the averages and
EV for light and effect parameters (a copy at a fixed lag would do); the GPU writer must run after the frame's constant
upload; resets and per-area constants must be passed each frame. Not done: see section 8.

### LAP2 part 2: the crash

The crash is a driver abort (0xc0000409 at amdvlk64+0x268b24d is abort()) when GPU-reachable memory is full. In all 13
traced crashes one thread was inside `vkCreateDescriptorPool` and never returned, right after a `vkAllocateMemory`
answered OUT_OF_DEVICE_MEMORY (even for 0.3 MB). At the crash: device heaps 2.3-2.8 GB against 486 MB "allowed" (the driver
spills to system memory), system heaps 4.2-5.2 GB of 7238 MB, sum 6.9-7.07 GB = the ceiling: our allocator fills both heaps
to the budget and leaves the driver no room for its own pools. Standalone reproduction without the game
(`kit\run\lap2_pool_oom.c`): 7680 MB held, abort at the third pool. The "image not made" path is safe. One real bug fixed:
`make_pool` ignored the result of `vkCreateDescriptorPool`.

Memory guard (`RX_VK_MEM_GUARD=1`, first off by default): refuses new memory blocks (not guest imports) and descriptor
pools when little of the system heap or of RAM is left (`_GTT_MB` 1024, `_RAM_MB` 512; sub-switches `_POOLS` / `_BLOCKS`).
A/B on the Kokiri teleport, 10 a side: without the guard 2 of 10 survive; guard 10 of 10; pools only 10 of 10; blocks only
10 of 10.
